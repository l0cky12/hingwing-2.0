# Verify Highwing

Highwing is an Electron viewer for the Hermes agent gateway. The surface a user touches is one desktop window: a bots sidebar, the open bot's chat list, a chat thread, a composer, approval cards and a connection banner. This skill drives that window through Playwright's Electron driver. Every run happens inside a private Xvfb display, so no window reaches the user's Hyprland desktop and two runs can go side by side.

Everything goes through one helper:

```
H=.claude/skills/verify/scripts/highwing-verify.mjs     # from the repo root
$H doctor                     # is this checkout worth driving?
$H build                      # electron-vite build of apps/desktop into apps/desktop/out
$H run [options] <steps...>   # launch, drive, screenshot, tear down; exit 0 only if every step passed
$H compare <run>              # reference | ours composites for every shot named after a reference
$H cleanup --run <run> | --all
```

## Launch

`run` launches the built app (`apps/desktop/out/main/index.js`) with the npm `electron` binary, never `/usr/bin/electron*`. It refuses to start when the build is older than any file in `apps/desktop/src`, `packages/hermes/src` or `packages/thread/src`. Run `$H build` first. Runs share the build read-only, so build once before starting parallel runs.

Options:

Every run names one gateway: `--fixture`, `--fake-host`, `--fake-webapp` or `--webapp-url`. Hermes, ssh and Tailscale are installed on this machine, and a run that named none would reach the real ones.

- `--fixture <path>` sets `HIGHWING_FIXTURE`. Main then plays that recorded gateway through the real client, and no socket or process outside Electron is touched. The app has no setup screen and no Settings in this mode.
- `--fake-host <scenario>` starts the fake Hermes machine of `packages/hermes/src/testing/fake-host.ts` and launches the app with the fake machine's bin directory as its whole `PATH`. That directory holds a fake `ssh`, `tailscale` and `hermes`, so the app runs its real setup check and its real remote dial and reaches nothing real. A tool the scenario lacks is a real "command not found". The scenarios are `ok`, `ok-bound`, `slow` and one per check failure: `tailscale-missing`, `tailscale-off`, `tailscale-signed-out`, `host-not-found`, `host-offline`, `unreachable`, `ssh-missing`, `ssh-denied`, `ssh-check`, `host-changed`, `hermes-not-found`, `hermes-too-old` and `cant-save`. The fake machine is `hermes-host.example-tailnet.ts.net`. Its gateway plays `fixtures/errand.jsonl`, or the file `--fixture` names. The Hermes of `ok` mints the ticket that reaches every bot, so the app can switch bots. The Hermes of `ok-bound` passes the same check and mints none, as an older Hermes does, so the app reaches one profile and refuses to switch.
- `--fake-webapp <scenario>` starts the fake Hermes Webapp of `packages/hermes/src/testing/fake-webapp.ts` in front of a gateway that plays `fixtures/errand.jsonl`, or the file `--fixture` names. The app is launched with an empty directory as its whole `PATH`, so it runs its real check, sign-in and dial by address and can run no real tool. The scenarios are `ok`, `too-old`, `ungated` and one per failure of a check by address: `url-unreachable`, `url-certificate`, `not-hermes`, `no-sign-in`, `dashboard`, `sign-in-cancelled`, `sign-in-timed-out`, `sign-in-refused`, `url-no-socket` and `url-legacy`. The run stands in for the user's browser: it reads each sign-in page main asked for from `opens.jsonl` and has the fake's user follow it. That user signs in at once, except in `sign-in-cancelled` and `sign-in-timed-out`, where the page is left open.
- `--login-form` needs `--fake-webapp`. The fake's `/login` then serves the form of Hermes's own sign-in page, and signs in only the username and password in the files that `HIGHWING_VERIFY_USER_FILE` and `HIGHWING_VERIFY_PASSWORD_FILE` name. The run opens each sign-in page in a browser window of its own, types the two into the form and submits it. It saves the page as `sign-in-page-<n>.png` before it types, and never writes either value.
- `--webapp-url <address>` reaches a real gateway's Webapp at that address, with the same empty `PATH`. It signs in on Hermes's `/login` page as `--login-form` does, with the two files. Everything the run writes names the gateway's host as `hermes.example.com`: each shot, each `.aria.txt`, `steps.log`, `opens.jsonl`, `main.log` and `console.log`. It plays no fixture.
- `--keyring test|system` needs `--fake-webapp` or `--webapp-url`. Without it the app is launched with `--password-store=basic`, so it has no keyring, keeps a sign-in for one run, and the run fails if `sign-ins.json` exists when it ends. `test` sets `HIGHWING_TEST_KEYRING`, and a build that is not installed then keeps sign-ins unsealed in `sign-ins.json`. It is refused with `--webapp-url`. `system` leaves the keyring to the desktop and puts `dbus-send` alone on the app's `PATH`, so the app can ask whether a Secret Service runs.
- `--sign-in-ms <ms>` needs `--fake-webapp` or `--webapp-url`. It sets `HIGHWING_SIGN_IN_MS`, which shortens the wait for the browser in a build that is not installed.
- `--saved none|local|remote|url|unreadable|newer` needs `--fake-host`, `--fake-webapp` or `--webapp-url`. It writes that `connection.json` into the run's user-data directory before launch. The default is `none`, a first run. `remote` saves the fake machine, and `local` saves this computer, where the fake `hermes` answers. Both need `--fake-host`. `url` saves the address of the run's Webapp, and needs `--fake-webapp` or `--webapp-url`.
- `--mode bots|chats` writes `{"version":1,"mode":…}` to `mode.json` in the run's user-data directory before launch, creating the directory on a first run, so the window opens in bot mode or chat mode. With `--fake-host` it is written after the user-data directory is emptied. Without it the directory is left as it was, so a run with a name used before opens in the mode that run left.
- `--theme system|light|dark` writes `{"version":1,"theme":…}` to `theme.json` in the run's user-data directory before launch, as `--mode` writes `mode.json`, so the window opens with that pick in Settings' Theme row. With System and no `--system-theme`, the window follows the desktop's own setting.
- `--system-theme light|dark` gives the app a D-Bus session of the run's own, whose desktop portal reports that light or dark setting, so a window on System follows it. The bus, `xdg-desktop-portal` and the GTK backend it starts run with `HOME` and every `XDG_*` directory inside the scratch directory and `GSETTINGS_BACKEND=keyfile`, and the app gets only the bus's address. The desktop's own setting is never touched: the run reads `org.gnome.desktop.interface color-scheme` before and after, and fails if it changed. Teardown stops the bus and everything it started. It does not go with `--keyring system`, since the run's bus has no keyring.
- `--hold-at tailscale|ssh|attach|relay` needs `--fake-host`. The fake tool that reaches that moment waits for the rest of the run. `ssh` pins the setup check at "Connecting to hermes-host".
- `--drop-after <event type or request method>` is verification scaffolding. It writes a copy of the fixture whose gateway closes the socket 50 ms after the first frame of that event type, or the first request frame of that method (`sudo`), and plays the copy instead. The copy is saved as `fixture-edited.jsonl` in the evidence directory. The client shows the dropped link until its redial lands about 1 s later.
- `--answered-elsewhere` is verification scaffolding for a fixture in which Hermes asks for things the window would otherwise have to answer, such as the requests of `fixtures/asks.jsonl`. It writes a copy of the fixture without the steps that wait for this client's answer to a request: each `answer` step that carries a result, and each `clarify.lock` and `connection.respond` call. The gateway then plays the `request.cancel` that follows each one as if another client had answered, so the story runs to its end. An `answer` step that carries an error stays, because the app sends that decline itself. It combines with the other fixture edits into one `fixture-edited.jsonl`.
- `--acted-elsewhere` is verification scaffolding for a fixture whose story makes calls the window has no control for yet, such as `fixtures/commands.jsonl` and `fixtures/panels.jsonl`. It writes a copy of the fixture without the steps that wait for them: each `prompt.resolve_unknown`, `prompt.replace_queued`, `prompt.cancel`, `prompt.steer_queued`, `session.steer`, `session.redirect`, `session.export`, `process.kill`, `session.control`, `rollback.list`, `rollback.diff`, `rollback.restore` and `message.react` call. The gateway then plays what followed each call, as when another client makes it. The messages and the approval answer are still the window's to send. The copy is saved as `fixture-edited.jsonl` in the evidence directory.
- `--window-makes <call,...>` needs `--acted-elsewhere`. It keeps the steps of those calls, so the window makes them and the story waits for each. A call is a method, such as `process.kill`, or `session.control:<action>` for one action, such as `session.control:goal.pause`.
- `--answer-here <method,...>` needs `--answered-elsewhere`. It keeps the `answer` steps of requests of those methods (`sudo`, `secret`), and the `clarify.lock` and `connection.respond` calls for a `clarify` batch or a `connection` card, so the window has to answer them. The gateway then waits for the window's answer, and an answer that carries a typed value matches the recorded `•••`.
- `--cancel <method>=<reason>` drops the `answer` step of the first request of that method and sets the reason of that request's `request.cancel` to `<reason>`, as Hermes withdrawing it. `sudo=shutdown` reads as withdrawn, `sudo=timeout` as nobody answering in time. The card is open from the request until the recorded cancel, about 1.5 s for the sudo of `fixtures/asks.jsonl`. It combines with `--answered-elsewhere` into one `fixture-edited.jsonl`.
- `--models <reply.json>` writes a copy of the fixture whose header carries that canned `model.options` reply, and plays the copy. The gateway then lists those models, starts the chat on the reply's `model`, and switches it on a `session.mutate` with operation `model`. Without it the gateway refuses `model.options` as an unknown method, as an older Hermes does. `fixtures/models/three.json` offers three models with `fast-small` current. `fixtures/models/none.json` offers none. It combines with `--drop-after` into one `fixture-edited.jsonl`.
- `--catalog <catalog.json>` writes a copy of the fixture whose header carries that canned `commands.catalog` reply, and plays the copy. Highwing runs a listed command it owns, such as `/busy`, itself. Without it the gateway refuses `commands.catalog` as an unknown method, unless the fixture's own header has one. `fixtures/catalog/busy.json` lists Hermes's `/busy` entry only. It combines with the other fixture options into one `fixture-edited.jsonl`.
- `--guarded <model,...>` makes a switch to those models need a second yes, as Hermes's guard does for a costly model. An idle switch answers with a confirmation. A switch held during a turn is asked about when the turn ends.
- `--usage <usage.json>` writes a copy of the fixture whose header carries that canned usage: `before` and `after`, two `session.stats` replies, and `breakdown`, a `session.context_breakdown` reply. The gateway then answers `session.stats` with `before` until the story's first turn ends and with `after` from then on, puts `after` on the turn's end as its usage, and answers `session.context_breakdown` with `breakdown`. Without it the gateway refuses both calls as unknown methods, as an older Hermes does, and the chat shows no context meter and no token counts. `fixtures/usage/errand.json` starts at 3 percent and ends the errand at about 34 percent with 1,204 tokens in, 380 out and 412 of reasoning. `fixtures/usage/nearly-full.json` ends it at 87 percent. It combines with the other fixture options into one `fixture-edited.jsonl`.
- `--profiles <reply.json>` writes a copy of the fixture whose header carries that canned `profiles.list` reply, and plays the copy. The sidebar then lists those bots. Without it the gateway refuses `profiles.list` as an unknown method, as an older Hermes does, and the sidebar says "This Hermes can't list its bots." `fixtures/profiles/roster.json` holds the six bots of the user's own Hermes, as the approved layout shows them. `fixtures/profiles/edge.json` holds thirty-one awkward ones, one of them hidden. `fixtures/profiles/marks.json` holds twenty, with a hidden default bot, a pinned bot and two more hidden bots. It combines with `--models` and `--drop-after` into one `fixture-edited.jsonl`. The gateway gives every bot whose row names a Bot Chat that chat, holding the row's preview as its one reply, and answers a message there with `<profile>: <text>`. The fixture's story is the default bot's Bot Chat. An untitled `session.create`, which a new chat's first message sends, makes an empty chat `chat-<profile>-<n>` in the routed profile that answers the same way. The file may also hold a top-level `chats` key, which maps a profile to the chats it has beside its Bot Chat. `run` moves it into the header's `chats`, so `profiles.list` never carries it. Each chat is `{ id, title, last_active, rows: [{ role, text }], asking?, hidden?, pinned?, branched_from? }`. One with `asking: { command, description }` resumes running, waiting on that approval. One with `hidden: true` is listed only to a call that asks for hidden chats, as a Bot Chat is. One with `pinned: true` is pinned, which a picker row says. A Bot Chat the roster names is pinned unless it is seeded, as the user's Hermes lists them. A `session.mutate` with operation `sidebar {pinned}` pins or unpins any of these chats, `archive` takes one out of the stored list, and `delete`, at the chat's generation and refused while its turn runs, takes it out of every list. One with `branched_from: <chat id>` was branched from that chat of the same profile, which `--tree` lists. One with `shown: <n>` resumes with only its newest n rows, the first marked `archived_truncated` as Hermes trims a long chat, and `session.transcript` still pages every row. A row may have `role: "tool"`, one step of its turn with no name or arguments. `session.list` for a profile other than the default lists its chats: stored by last use, and live only the ones that wait. A `session.mutate` that renames one of these chats retitles it, and `session.export` renders its title and messages under Hermes's file name, `hermes_session_<id>.<format>`. `fixtures/profiles/chats.json` gives Research no Bot Chat and three chats, one of them waiting. A chat seeded with the id of a bot's `canonical_session` is that bot's Bot Chat, with the seeded rows in place of the one preview row. Give it `"title": "Bot Chat"` and `"hidden": true`. The file may also hold a top-level `relay` key, which `run` moves into the header's `relay` the same way. It maps a profile to what its bot does with a message handed to it by `bot_relay.deliver`: `{ reply, delay_ms? }` answers with that one reply after the delay, and `{ refuse }` refuses with that reason. A profile with no entry is refused as `runtime_unavailable`. Without the key the gateway refuses every `bot_relay.*` call as an unknown method, as a Hermes without the bot relay does, and `@` opens no list. `fixtures/profiles/team.json` holds Ada, Sam and Rae, with Rae answering after 1500 ms and Sam not running. The file may also hold a top-level `turn_ms` key, which `run` moves into the header's `turnMs`. It maps a profile to how long each turn of its chats takes, in ms: a message starts its turn at once, the chat is listed as running and as `working` by `session.active_list`, and the reply ends the turn that long after. A profile not in it answers before the next frame is read. `session.active_list` lists a profile's running chats, `waiting` for one with an `asking` approval, and the story while its turn runs, `waiting` while it holds an approval or a request. `fixtures/profiles/activity.json` is `chats.json` with dr eggbot's turns taking 6000 ms. The file may also hold a top-level `groups` key, which `run` moves into the header's `groups`: the home profile's group chats, `{ driver?, seatable?, rooms? }`. `driver` is what `groups.capabilities` says of whether Hermes runs them now, default true, and Hermes makes a group either way. `seatable` lists the profiles Hermes would seat, default every profile, or is null for a Hermes that names none. Each room is `{ id, name, members: [{ profile, handle }] }` with 2 to 6 members, most recently changed first. The gateway answers `groups.capabilities`, `groups.list` and `groups.create` with Hermes's rules: closed key sets, 2 to 6 seats, unique handles, a bot it would not seat refused on field `members`, and one group per id, a repeat answered with the group it made. Without the key every `groups.*` call is an unknown method, as on a Hermes without group chats. `fixtures/profiles/launch.json` holds the seven bots of the approved group chat mock with `groups: {}`. A room may also carry `log`, lines it already holds (`{ user }` or `{ member, text }`), and `groups` may carry `turns` and `change_events`. `turns` maps a profile to what its bot does with each turn it gets, in order: `{ reply, delay_ms? }`, `{ fail, delay_ms? }` or `{ hold: true }`, which thinks until Stop or a newer message. A profile with no turn left passes. The gateway then answers `groups.state`, `groups.log`, `groups.send`, `groups.stop`, `groups.rename` and `groups.disband` too: a message starts round 0 with the members it `@`-mentions, or all of them, in roster order, a reply that `@`-mentions a member gives that member another round, and each change pushes `groups.changed` unless `change_events` is false. `fixtures/profiles/launch-group.json` holds Launch plan and the turns of the approved open group.
- `--paths <file.json>` copies that file into the fixture header's `paths`: `{ cwd?, words }`. `words` maps a typed word such as `@not` to the `complete.path` reply as Hermes sends it, and a word not listed answers `{ items: [] }`. `cwd` becomes the story chat's working folder, which the `@` list names under its files. It writes a copy of the fixture with the served origin in place of every `http://localhost:5173`, a URL that a reply streams in two pieces included, and plays the copy. - `--configure-clash <title>` needs `--profiles`. It sets the header's `configureClash`. It combines with the other fixture options into one `fixture-edited.jsonl`.
- `--approvals manual|smart|off` needs `--yolo`. It sets the header's `approvals`, every bot's approval mode, which the gateway then answers to `config.get` of `approval_mode` and changes on `config.set` of it, as Hermes does. `info.yolo` stays the chat's own flag. Without it the gateway refuses both.
- `--yolo-denied` needs `--yolo`. Every YOLO set is then refused `permission_denied`, as Hermes refuses a viewer without control of the chat.
- `--yolo-elsewhere-after <event type>` needs `--yolo`. It adds a `session.info` frame with `yolo: true` 50 ms after the first frame of that type, and moves the seq of every later frame of the session up by one. It stands for another client turning YOLO on.
- `--pick <path[,path]>` sets `HIGHWING_PICK_FILES` to those files, each resolved from the repo root. Main then answers every press of the paperclip ("Attach files") with them, in that order, and opens no file dialog. Without it a press opens the system dialog, which nothing in a run can answer.
- `--attach-limit <bytes>` writes a copy of the fixture whose header carries `attachLimits` with that many bytes for both an image and a file, and plays the copy. Main then refuses to attach a larger file, in words that name the file and the limit. Without it the limits are Hermes's own: 25 MiB for an image and 256 MiB for a file. It combines with the other fixture options into one `fixture-edited.jsonl`.
- `--menu-pick <label>` sets `HIGHWING_MENU_PICK`. Main then runs the entry with that label each time it records a context menu that holds it, enabled, as if the user picked it. A run without it removes any `HIGHWING_MENU_PICK` it inherited.
- `--arg <value>` appends one argument to the app's command line, such as a `highwing://chat/<session id>` link, as a launch from the desktop passes it.
- `--size <width>x<height>` sets the window's content size before the first step, and the size every `shot` must have. The default is 1180x860.
- `--chat-only` makes the size above the size of the chat column. The window grows by the width of whatever sits left of the chat, the 288 px column of either mode, and every `shot` is clipped to the chat column. The ARIA snapshot still covers the whole page. Use it for any shot that a tool reads as a chat with no sidebar: the design C references, `forced-colors-check.mjs` and `chat-parity.mjs`.
- `--forced-colors` emulates the desktop's forced-colors (high-contrast) mode in the first window once it opens, before any step runs, so the window draws only with system colors.
- `--more-contrast` emulates `prefers-contrast: more`.
- `--reduced-motion` emulates `prefers-reduced-motion: reduce` in the first window once it opens, and again after a `relaunch`, so animations stop and the page draws its static marks.
- `--video` records the window with Playwright's `recordVideo` at the `--size` (default 1180x860, and not clipped by `--chat-only`) and saves it as `video.webm` in the evidence directory at teardown. The window then stays still for 700 ms after each step, so a viewer can follow the run, which makes the run slower. The run fails if the video cannot be saved. Use it for a recording of a feature in use, not for timing.
- `--latency <ms>` needs `--fixture`. It sets `HIGHWING_FIXTURE_LATENCY_MS`, and the scripted gateway then writes each reply that many ms after the call arrived, as a busy Hermes answers. Every other frame is written at once, unless a held reply is still ahead of it, so the client reads frames in the order the gateway wrote them. The default is 0, which holds nothing. Main refuses anything but a whole number of ms.
- `--timed-shot <ms[,ms]>` makes each `timed` step also save `<label>-at-<ms>ms.png` that many ms after the click, as the window drew it then. A screenshot during the click slows it, so do not report the time of a run that takes one.
- `--cpu-profile` makes each `timed` step sample the renderer through CDP and main through its own inspector, every 100 µs, from just before the click until the result is drawn. It saves `<label>.renderer.cpuprofile` and `<label>.main.cpuprofile`. Profiling slows the window, so do not report the time of a profiled run. Build with `pnpm --filter @highwing/desktop exec electron-vite build --sourcemap` first, so `switch-bench.mjs top` can name the source of each renderer function.
- `--run <name>` names the evidence directory. The default is a timestamp plus the PID.
- `--timeout <ms>` is the per-step limit. The default is 15000.

Every run sets `HIGHWING_OPEN_LOG` to `opens.jsonl` in the evidence directory. Main then records each request to open a file, show its folder, or open a link in the browser in that file, and opens nothing on the desktop. A run without `--pick-file` removes any `HIGHWING_PICK_FILE` it inherited. Every run also sets `HIGHWING_SAVE_DIR` to `saves/` in the evidence directory. Main then writes an exported chat there under Hermes's file name, and opens no save dialog.

A run with neither `--theme` nor `--system-theme` emulates a light `prefers-color-scheme`, as every run did before the theme existed, so its shots stay comparable whatever the desktop is set to. A Dark pick in Settings then changes nothing on the page. A run with either one turns the emulation off, so the page draws what main and the desktop ask for.

Every run also sets `HIGHWING_NOTIFY_LOG` to `notices.jsonl` in the evidence directory. Main then records each desktop notification there as a JSON line (`sessionId`, `turnId`, `title`, `body`) and shows nothing on the desktop.

Every run also sets `HIGHWING_MENU_LOG` to `menus.jsonl` in the evidence directory. Main then records each context menu it would have shown there as a JSON line, `{ items, disabled? }`: `items` lists the entries' labels in order, with `"separator"` for a separator, and `disabled` lists the labels of the entries that are disabled. Nothing pops up.

A JavaScript dialog the page opens (`alert`, `confirm` or `prompt`) is logged to `steps.log` as `DIALOG`, dismissed, and fails the run once the steps end. The app never opens one, so a dialog means script ran that should not have.

Ready means the first window has loaded. Use `wait window` as the first step.

The window's content area is 1180x860, the size of the reference screenshots, unless `--size` or `--chat-only` changes it. `run` passes `--ozone-platform=x11`, `--force-device-scale-factor=1` and `--disable-gpu`, and removes `WAYLAND_DISPLAY`. Electron 45 would otherwise pick Wayland and open the window on the real compositor. `run` also checks that the X server on its display was started by its own `xvfb-run`. Plain `xvfb-run -a` gives two runs started together the same display, and the first teardown would then kill the other run.

Teardown is part of `run`. The app is closed and then killed by PID if it is still alive, whether the steps passed or failed. A `--fake-host` run then fails if a fake tool the app started is still running, because the app must end its own ssh processes when it quits.

## Doctor

`$H doctor` is read-only. It checks node, `xvfb-run`, `magick`, `playwright-core`, the downloaded electron binary, whether the build is current, and that `tsx` is installed to run the fake host. It also lists verify instances that are still running. Every line must read `ok` before you trust a run. A `note` about running instances means an earlier run did not tear down; `$H cleanup --all` stops them.

A `/regex/` name is any name that starts and ends with a slash, as `count` already takes. It is case-sensitive. A step that finds several matches uses the first, except `count`, `focused` and `gone`, which look at all of them. Use one for a name that holds a time or a goal, such as `button /^Thought/`.

| `setup-checking` | the connection card shows the step a check is at (`role=status`, name "Checking") |
| `setup-failed` | the connection card shows a failure (`role=alert`) |
| `setup-saved` | the first run's saved screen's "Open chat" button is shown |
| `settings` | the Settings page's heading is shown |
| `live` | the composer's Send button is enabled, so the chat is attached and the link is online |
| `tool-running` | a single step whose title starts with "Running" carries the live end (`[data-end="live"]`) |
| `approval` | the "Run this command?" card's "Run once" button is enabled |
| `settled` | the turn's end is the Done ring (`[data-end="done"]`) |
| `drawn` | the last reply that holds a diagram has none still drawing, so each is drawn or shows why it could not be (`.diagram[data-state]`) |
| `offline` | the connection banner (`role=status`, name "Connection") is shown |
| `regenerate` | the thread's "Regenerate" button is enabled, so the chat is idle and its last turn has a stored message to cut before |
| `slash-menu` | the composer's "Commands and skills" listbox is shown |
| `mentions` | the composer's "Mentions" listbox is shown |
| `relay-waiting` | a message handed to another bot says it waits for that bot (`.turn.relay [role="status"]`) |

| `preview` | the preview pane beside the chat is shown (`role=region`, name "Preview") |
| `helper-running` | a helper that has started work, not one still waiting to start, carries the live end (`.helper[data-end="live"]` whose hidden state reads "working") |
| `group-thinking` | an open group chat's thread ends in a live end that says a member is thinking (`#transcript .tip.thinking`, "Sam is thinking" or "Ada and Sam are thinking") |
| `group-replied` | an open group chat's thread holds a member's reply and no live end, so no member is answering |

`wait` polls with no backoff. The errand's listing step lives about 144 ms at recorded timing. Playwright's own `waitFor` spaces its polls up to 500 ms apart and missed it 3 times out of 3, while this loop caught it 5 times out of 5.

Main draws the preview pane's page in a view of its own, over the window, and a page screenshot cannot see it. When that view is shown, `shot` captures it from main and draws it onto the PNG at its place, and logs that it did. A shot with no pane shown is the page screenshot alone, as before. The ARIA snapshot never holds the page's text: use `page-says`.

`shot` fails when the image is not 1180x860, or the size `--size` names. After a `wait`, `shot` also fails if that state ended before the screenshot finished. A passing shot therefore shows the moment it was named for. Screenshots disable animations, so the live end's halo pulse never shows.

## Evidence

Each run writes to `/tmp/highwing-verify/<run>/`:

- `steps.log` lists every step with a timestamp, and ends with `PASS` or `FAIL`.
- `<name>.png` and `<name>.aria.txt` hold each shot and the ARIA snapshot of the page at that moment.
- `<name>.clip.txt` holds the clipboard text that a `clipboard` step read.
- `opens.jsonl` holds one JSON line for each open or show call that main accepted, and each page main asked the browser for.
- `sign-in-page-<n>.png` is Hermes's sign-in page before the run typed into it (`--login-form` and `--webapp-url` runs).
- `notices.jsonl` holds one JSON line for each desktop notification main would have shown.
- `menus.jsonl` holds one JSON line for each context menu main would have shown.
- `bus.log` holds what the run's own D-Bus session and the services it started printed (`--system-theme` runs).
- `main.log` holds the Electron main process's stdout and stderr. `console.log` holds the renderer console and page errors.
- `failure.png` is the window when a step failed.
- `video.webm` is the recording of a `--video` run.
- `timings.jsonl` holds one JSON line for each `timed` step.
- `gateway-calls.jsonl` holds every frame the client sent the scripted gateway, one per line, as it arrived (`--fixture` and `--fake-host` runs). A typed answer's `value`, a connector card's credentials and a `vault.unlock`'s `password` are written as `•••`, so the file proves a value was sent and never what it was. Main writes it when `HIGHWING_FIXTURE_CALLS` names a file, which `run` always sets, and the fake host writes it from the same variable, which `run` passes it.
- `compare-<name>.png` comes from `$H compare <run>`. It puts the reference on the left and the shot on the right. Shots named `tool-running`, `approval`, `settled` and `settled-expanded` pair with `docs/design/reference/tool-running-C.png`, `approval-C.png`, `settled-C.png` and `settled-C-expanded.png`. Those four references show the chat with no sidebar, so take their shots with `--chat-only`. A shot named `bots-approved` pairs with `bots-sidebar.png`, the approved sidebar layout, and shows the whole window.

`node .claude/skills/verify/scripts/switch-bench.mjs` times how long the window takes to show the result of a switch, on `fixtures/profiles/bench.json` (made by `fixtures/make_bench_fixture.py`): Emu, the default bot, Atlas, whose Bot Chat holds 160 rows of markdown (about 290 KB), Birch, with a short Bot Chat and 40 chats, and Cedar, with no Bot Chat and 3 chats. Each scenario is one `timed` click in a fresh launch with a fresh run name, run 7 times (`--runs`) at each latency of `--latencies` (default `0,75`), one after another, the latencies taking turns so drift favors neither. `mode-to-chats` and `mode-to-bots` switch modes until the other column shows a row. `bot-first-list`, `bot-first-thread` and `bot-first-name` pick Birch, Atlas and Cedar for the first time, a second after the bots are listed, as a user takes that long to open the picker, until Birch's newest chat is listed, Atlas's last message is in the thread, or the picker names Cedar. `bot-return-list` and `bot-return-thread` come back to Birch or Atlas a second or so after leaving it. `bot-first-whole` and `bot-return-whole` are the two thread scenarios timed until Atlas's first message is in the thread, which is when every turn of the chat is drawn and not only its newest. `bot-return-cold-thread` comes back to Atlas after main released it, which `reached session.detach` waits for, about 60 s, so it runs 3 times at 75 ms only. It prints the median, min and max of each scenario and latency, and the median longest frame, writes them with every sample, its run and the calls its click made to `/tmp/highwing-verify/<id>/bench.json`, and exits non-zero when a run failed or a scenario has fewer samples than it wanted. Each run's evidence stays in `/tmp/highwing-verify/<id>-<scenario>-l<latency>-<n>/`, and its scratch directory is removed. `--only a,b` runs some scenarios. `--shots` runs each bot scenario once at 75 ms with `--timed-shot 30,90` and prints the screenshots' paths. `--profile` runs `mode-to-chats` and `bot-first-thread` once at 0 ms with `--cpu-profile` and prints each profile's top functions. `switch-bench.mjs top <file.cpuprofile> [n]` prints the n functions with the most self time, each with the source file and line the build's source map gives it. A number means nothing until the calls in `bench.json` show the click made the calls you expect.

`node .claude/skills/verify/scripts/chat-parity.mjs <before-run-dir> <after-run-dir>` counts the pixels that differ between the shots of two runs, name by name. It ends in `PASS` only when every pair differs by zero. A missing shot, a size mismatch and a run with no shots are `FAIL`. `--self-test` proves it reports each of those.

Proof standards:

- Drive the real user path. Type into the composer and press Send. Click the approval button. Never call the bridge or set state from the test.
- Capture the action and the state it caused: a shot before and after, plus the ARIA text that names the change.
- A fixture is the production boundary for Hermes. In a `--fake-host` run the boundary is the three commands the app runs: `ssh`, `tailscale` and `hermes`. In a `--fake-webapp` run the boundary is the Webapp's HTTP routes, its socket and the user's browser. Nothing else is mocked.
- Never launch the app for a check without `--fixture`, `--fake-host`, `--fake-webapp` or `--webapp-url`.
- A `--fake-webapp` run fails if a token, a code or a ticket the fake made is in any evidence file or in any file under the app's user-data directory.

## Cleanup

`$H cleanup --run <name>` or `$H cleanup --all` kills only the PIDs this skill recorded in `/tmp/highwing-verify-scratch/<run>/pid`, `host-pid`, `second-pid`, `browser-pid` and `bus-pid`: the app, its fake host or fake Webapp, a second instance, the sign-in browser and the run's own D-Bus session. The portal services that bus started exit once it is gone. It then deletes that scratch directory, which holds the Electron user-data dir. It never touches `/tmp/highwing-verify/`. Never kill Electron by process name, because the user may be running their own.
