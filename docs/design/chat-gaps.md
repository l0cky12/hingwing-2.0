# Chat gaps: Hermes chat and Highwing chat

This page lists every chat feature of Hermes's own clients, what Highwing does today, and what the `hermes-gateway-v1` contract offers for it. It was read from the source of Hermes 0.23.3 at `be787439` on 2026-11-24. `chat-parity.md` decides how the backend serves the gaps.

Paths: `H:` = /home/liam/.cache/hw143/src/hermes-agent (Hermes 0.23.3, be787439). `HD:` = H:apps/desktop/src. `TUI:` = H:ui-tui/src. `GW:` = H:gateway. `TC:` = H:tui_gateway/contracts. `HW:` = Highwing repo root. `HWP:` = HW:packages/hermes/src.

Every cite below was read for this pass unless it says "(explorer cite)".

## 1. Overview

Hermes has two chat clients that matter: the Ink TUI and the Electron Desktop. The web dashboard's chat is the real `hermes --tui` running in a PTY over `/api/pty` (H:web/AGENTS.md:7-23), so it adds nothing. On the canonical `hermes-gateway-v1` route both clients talk to the session authority, the same owner Highwing talks to. A method is served when `AuthorityConnection.handlers()` names it (GW:session_controls.py:239-311). On a WebSocket, a method the authority answers with -32601 can still reach the legacy sidecar handler if the ticket holds the full interactive grant and the method is outside the `session.`/`prompt.`/`message.` namespaces (H:tui_gateway/ws.py:402-409, H:tui_gateway/ws_legacy_fallback.py:31-62). Desktop also uses REST `/api/sessions*` for its sidebar and `/api/audio/*` for voice, and the gateway contract cannot carry either.

Highwing today covers the core loop: send, a server-side queue it can see but not edit, streamed text and interim commentary, tool steps with diffs, approvals and single-answer clarify, Stop, history with paging, the model picker, the slash menu for 33 gateway-run commands, Bot Chats, and auto-titles. Almost every gap is in `packages/hermes`. The wire layer drops the event (it is in `UNSHOWN`), or the `Command` union has no verb for a served method. Only voice/read-aloud, and tool images on a remote Hermes, are beyond the contract.

Counts in the gap table (61 rows): **done 13, frontend only 6, backend missing 41, contract can't 1**. Two `backend missing` rows also say what the contract cannot do: tool images on a remote Hermes, and the Desktop window bridges.

## 2. How chat works in Hermes's clients

**Send and queue.** `prompt.submit {session_id, text, submission_id|input_id, attachments?, clarify_batch?, display_kind?, title_preview?, api_text?, model_override?}` (TC:canonical_sessions.py:249-275). A submit while a turn runs becomes a queued admission in the owner's FIFO. Queue rows arrive in the snapshot `pending` and in every `session.info` (GW:session_authority.py:486-496). Each row is `CanonicalPendingAdmission` and carries `controls: ['steer','replace']` and `steering` (TC:canonical_sessions.py:97-106). Desktop: send HD:app/session/hooks/use-prompt-actions/submit.ts:1160. Queue row actions are cancel `prompt.cancel {session_id, admission_id}`, send-now `prompt.steer_queued {session_id, admission_id}`, and edit `prompt.replace_queued {session_id, admission_id, submission_id, text, attachments?}` (HD:app/chat/composer/discard-lost-prompt.ts:29,44,61; TC:canonical_sessions.py:290-303,377-391). TUI: TUI:app/submissionCore.ts:138-155, and queue cancel / resolve-unknown at TUI:hooks/useQueue.ts:246-255.

**Lost turn after an owner restart.** An admission recovered as `unknown` pauses the FIFO until a client calls `prompt.resolve_unknown {session_id, admission_id, execution_generation}`. The generation must be the one on the row (GW:session_authority.py:907-914; TC:canonical.py:72-80). Desktop: HD:api/canonical-protocol.ts:263,428-434. TUI: TUI:hooks/useQueue.ts:246-255. The owner resolves the row itself only when the last viewer closes the session.

**Busy input: steer, redirect, interrupt.** Busy mode is a per-session UI setting, `config.get/set {key:'busy', value: interrupt|steer|queue}`. A `gui` launch defaults to `interrupt` and a `tui` launch to `queue` (GW:session_busy_controls.py:30-72). `session.steer` and `session.redirect` take `{session_id, execution_generation, text}` and answer `{status: queued|redirected|rejected, text, execution_generation, authority_epoch, delivered?}` (GW:session_busy_controls.py:181-221; TC:canonical_sessions.py:305-327). Desktop: HD:app/session/hooks/use-busy-input-mode.ts:63 and HD:app/session/hooks/use-prompt-actions/slash-session-commands.ts:356-380. TUI: TUI:app/steerOrQueue.ts:28 and TUI:app/useSubmission.ts:301.

**Stop.** `session.interrupt {session_id, execution_generation}`. Desktop: HD:api/canonical-protocol.ts:420-426.

**Streaming text.** The stream is `message.start`, then `message.delta {text|null, turn_id, segment, offset}`, where null text seals a segment before a tool round. `message.interim {text, already_streamed, turn_id, segment}` hands over commentary whole. `message.complete {…, persisted_turn {row_ids, user_row_id, final_assistant_row_id, user_row_ids, submission_id, complete}}` ends the turn (TC:events.py:153-196,263-279).

**Reasoning.** `reasoning.delta {text}` streams the model's reasoning, and `reasoning.available {text}` delivers a whole block from a non-streaming provider. Both go out only when the session shows reasoning (GW:local_viewer_events.py:50-54,142-147). The session flag `config.set {key:'show_reasoning'}` wins (GW:session_busy_controls.py:90-108). With the flag unset, the session's own launch source decides: a `gui` or `tui` launch shows reasoning unless `display.show_reasoning` is off, and any other source shows none (GW:local_viewer_events.py:61-87). History assistant rows carry `reasoning` as a sidecar key (TC:common.py:168-186). Desktop: HD:app/session/hooks/use-message-stream/gateway-event/message-stream.ts:312,324. MoA progress (`moa.*`) uses the same gate.

**Tools.** The tool events are `tool.generating {name}`, `tool.start {tool_id, name, args}`, `tool.progress`, and `tool.complete {tool_id, name, args, duration_s, result, result_text, inline_diff, todos, revision, image_path}`. A local viewer's turn adds `duration_s`, `inline_diff`, `image_path` and todos (GW:local_viewer_events.py:207-232; GW:run_turn_progress.py:1070-1078). `image_path` is a file on the Hermes host. Desktop loads it through its authenticated REST media pipeline (HD:components/assistant-ui/tool/fallback-model/index.ts:805-816).

**Approvals.** The `approval.request` event (untyped in the contract) carries `{kind, prompt_id, execution_generation, command, description, choices, timeout_s?, edit?}`. Choices are `once` and `deny`, plus `session` and `always` unless the request forbids them (GW:session_pending_controls.py:18-38). The answer is `approval.respond {session_id, execution_generation, prompt_id, choice}`, exactly those keys (GW:session_controls.py:995-999). `approval.settled {prompt_id, execution_generation}` closes the card. Desktop puts a confirm dialog in front of "Always" (HD:components/assistant-ui/tool/approval.tsx:245-246,391-411). It sends `approval.received` (HD:store/prompts.ts:256), a read-only ack that only reports whether the request is still pending (GW:session_ancillary.py:201-223; H:tools/approval.py:289-292). The TUI's "No, and tell Hermes instead" steers the text into the held turn first, then denies (TUI:app/useApprovalAnswers.ts:63-84).

**Clarify.** By default the clarify tool asks one question per card through the `clarify.request` event `{kind, prompt_id, execution_generation, question, choices, multi_select, timeout_s?}` (GW:session_pending_controls.py:40-51). The answer is `clarify.respond {session_id, execution_generation, prompt_id, answer}`, and `answer: ""` skips (GW:session_pending_controls.py:96-104). A multi-select answer is a JSON array string of choice labels, such as `'["staging","prod"]'` (TUI:components/prompts.tsx:290; HD:components/assistant-ui/clarify/pending.tsx:154-159). The tool decodes it, and a non-JSON string counts as one typed "Other" answer (H:tools/clarify_tool.py:36-47). A local viewer whose submit sets `clarify_batch: true` gets the whole batch as one `clarify` server request instead. It can lock answers one at a time with `clarify.lock {request_id, question_id, answer}` and finishes with `{answers:{qid: str|null}, outcome?}` (GW:session_cli_turn.py:181-188; GW:session_clarify_batch.py:16-42; TC:server_requests.py:36-60). Both Desktop and the TUI declare it (HD:api/client.ts:457; TUI:app/submissionCore.ts:153-154). A plugin command's choice prompt always uses the `clarify` server request on a local session (GW:plugin_command_choice.py:10-11).

**Masked prompts: sudo, secret, vault.** For a local viewer's turn, the owner writes a JSON-RPC request `{id:"srq-…", method:"sudo"|"secret"|"vault.*", params:{session_id, …}}` to every attached transport and blocks the agent thread for up to 120 s (GW:session_sudo_prompt.py:22-53; GW:session_secret_prompt.py:30-49; GW:session_server_requests.py:171-209). The reply is a response frame `{id, result:{value}}`, where `""` means skipped. A secret is saved to the profile's `.env` and never reaches the model. Desktop: HD:components/prompt-overlays.tsx:66-95.

**Retry and undo.** Desktop's `/retry` and `/undo [N]` read a fresh `session.resume` snapshot. They take the Nth newest live user row from `messages`: role `user`, no display kind or `steer`, an integer `row_id`, not `archived`, and not a compaction marker. They send `session.mutate {operation:'rewind', payload:{target_message_id: row_id}, request_id, expected_revision, expected_generation}` (HD:app/session/hooks/use-prompt-actions/slash-session-commands.ts:91-131,219-255). `derived_target` and `replay_only` are flags local to Desktop. HD:api/canonical-protocol.ts:362-386,451 uses them to retain and replay the request, and they never go on the wire. `/retry` then resubmits the receipt's `target_message.content` (:331-351). `/undo` puts it back in the composer and asks `rollback.list {undo_since, undo_message_id}` for a file hint (:258-271,304-325). TUI: TUI:app/slash/canonicalRewindPicker.ts:215.

**Edit, restore, regenerate.** All three rewind to a user row and then submit. Desktop's legacy truncate keys become `rewind {target_message_id: truncate_before_row_id}` followed by a plain submit (HD:api/canonical-protocol.ts:159-179). "Restore" on a user bubble and "Refresh" on a reply take the same path (HD:app/session/hooks/use-prompt-actions/index.ts:1180-1230; HD:components/assistant-ui/thread/assistant-message.tsx:1426).

**Branch.** `session.mutate {operation:'branch', payload:{through_message_id?, title?}}` needs `session:create` and answers `branched_session_id` (H:persistence/authority/runtime.py:299-310; GW:session_mutations.py:166). Desktop: HD:app/session/hooks/use-session-actions/index.ts:2640-2647.

**Attachments.** `image.attach_bytes {session_id, content_base64|data, filename?, ext?}` stages an image and answers `{path, mime, name, …}` (GW:session_images.py:8-45). `prompt.submit` then takes `attachments: [{path, mime}]`. `file.attach {session_id, path|data_url|staged_upload, name?}` answers `{ref_text:"@file:…"}`, which goes into the prompt text, and the server expands `@file:` and `@url:` (GW:session_ancillary.py:137-180; GW:session_context_refs.py:18-24). Desktop: HD:app/session/hooks/use-prompt-actions/index.ts:184,209. A large paste becomes a text attachment (HD:app/chat/composer/large-paste.ts, explorer cite).

**`@` completion.** `complete.path {session_id, word, cwd?}`, rooted at the session's own cwd (GW:session_complete_path.py:15-40). Desktop: HD:app/chat/composer/hooks/use-at-completions.ts:233.

**Session controls through `session.mutate`.** The operations are rename, archive, sidebar (`pinned`, `unread`, `hidden`, `title`, `archived`), delete, reset, compress, model, reasoning, workspace, edit_policy, editor_mcp, branch, rewind and import (H:persistence/authority/runtime.py:133-373; parsers :299-366). Desktop uses REST for list, search, delete and pin (HD:api/sessions.ts:124,459,729). `/compress` uses `session.compress`, and canonical-protocol.ts turns that into the `compress` mutation (HD:app/session/hooks/use-prompt-actions/slash.ts:855). Every committed mutation publishes `session.updated` (GW:session_mutations.py:350-354).

**Side prompts.** `prompt.btw {session_id, text}` and `prompt.background {session_id, text}` answer `{task_id}` at once. The answer arrives later as `btw.complete {task_id, question, text}` or `background.complete {task_id, text}` (GW:session_tui_side.py:1-10,175-224). Desktop: HD:app/session/hooks/use-prompt-actions/slash.ts:730,753-782. TUI: TUI:app/slash/commands/session.ts:121,142.

**Status around the composer.**
- Usage: `session.usage` (GW:session_usage.py:190-197) and `session.context_breakdown` (HD:app/shell/hooks/use-context-breakdown.ts:163).
- Todos: `todo.updated {todos, revision}` and the snapshot's `todo_state` (GW:run_turn_progress.py:1076-1078; HD:app/session/hooks/use-message-stream/gateway-event/tools.ts:114).
- Subagents: `subagent.*` events plus `subagent.list`, `subagent.tail`, `subagent.steer` and `subagent.interrupt` (GW:session_ancillary.py:24-34,37-60; HD:app/chat/composer/status-stack/subagent-transcript.tsx:37).
- Processes: `process.list` and `process.kill` (HD:store/composer-status.ts:443,504).
- Goal, loop and heartbeat: `session.control.read`, `session.control {action, args}` and the `session.control.update {control}` event (GW:session_control_actions.py:138-164; HD:store/session-control.ts:776,844).
- Status lines: `status.update {kind, text}` for compaction progress and `/goal` verdicts (GW:run_turn_progress.py:1215-1219; GW:run_goals.py:238-246).
- Notices: `notification.show` and `notification.clear` (GW:run_turn_progress.py:1120-1125; HD:app/session/hooks/use-message-stream/gateway-event/status.ts:275,305).

**Message actions in Desktop** (HD:components/assistant-ui/thread/assistant-message.tsx:1401-1520, user-message.tsx:590-735): copy, copy full response, branch into a new chat, read aloud, refresh (regenerate), an emoji reaction (`message.react {session_id, row_id|newest_role, emoji}`, GW:session_reactions.py:13-55), turn duration, and edit and restore on user bubbles. Export: `session.export {format, redact}` answers `{filename, content}` and the client writes the file (TC:canonical.py:332-350; HD:app/session/hooks/use-prompt-actions/slash-desktop-commands.ts:416).

**Title.** An auto-title republishes `session.info`, and its `title` comes from the stored row (GW:run_turn_progress.py:1156-1167; GW:session_local.py:590).

**Voice.** Desktop records and speaks through REST: `/api/audio/transcribe`, `/speak`, and the `*-stream` WebSockets in H:hermes_cli/web_routers/audio.py:89,527 (HD:api/system.ts:189-266). The TUI calls `voice.record` (TUI:app/useInputHandlers.ts:655). No `voice.*` method is among the authority's handlers. The call reaches the legacy sidecar through the fallback, and that sidecar records from the Hermes host's microphone and plays `voice.tts` on its speakers (H:tui_gateway/methods_voice.py:815-903).

**Shell.** The TUI's `!cmd` calls `shell.exec {session_id, command}`. It runs only for a local session, in that session's cwd (GW:session_shell.py:25-40; TUI:app/useSubmission.ts:168). Desktop does not use it.

## 3. What Highwing's chat does today

- **Send.** `actor.send` sends `prompt.submit {session_id, text, input_id, api_text?}` and resends it on reconnect (HWP:actor.ts:142-163,86-89). The composer is text only. There is no attachment, paste or drop handling (HW:apps/desktop/src/renderer/composer/Composer.tsx).
- **Queue.** Queue rows from `pending` and `session.info` feed the outbox. A row shows "Sending" or "Queued" with no actions (HWP:wire/parse.ts:144-149,276; HW:apps/desktop/src/renderer/chat/Thread.tsx:138,253-259). `discard` drops the local outbox entry only and sends no `prompt.cancel` (HWP:domain/reduce.ts:488-489). `admissionOf` drops `execution_generation`, `controls` and `steering`. An `unknown` row is ignored (HWP:domain/reduce.ts:420-421).
- **Stream.** `message.delta` uses segment and offset fencing. `message.interim` seals or pushes a text item, so interim commentary is shown (HWP:wire/parse.ts:216-224; HWP:domain/reduce.ts:545-561). `thinking.delta` only keeps the spinner alive (parse.ts:238). `message.complete` keeps `persisted_turn.row_ids` but not `user_row_id` (parse.ts:226-236).
- **Tools.** It handles the generating, start, progress and complete events, parses `inline_diff` into file diffs, and classifies results (parse.ts:239-266,599-656). It ignores `image_path`, `todos`, `summary` and `labels`.
- **Prompts.** Approvals render as four buttons labelled from `choices`, with the command shown (HW:packages/thread/src/thread-view.ts:427-464). Clarify shows choice buttons and a free-text box, and the answer is one string (HW:apps/desktop/src/renderer/chat/Thread.tsx:33-66; HWP:actor.ts:185-204). `multi_select` is parsed into `ask.multi` and not used (parse.ts:136). `timeout_s` and `edit` are dropped (parse.ts:128-140).
- **Server requests.** Every one is answered with a -32601 error frame and a "can't show" notice in the turn: sudo, secret, clarify batch, vault and Desktop bridges (HWP:hub.ts:127-131,171; HWP:wire/link.ts:422-424; HWP:domain/reduce.ts:241-244; thread-view.ts:474-484). Snapshot `open_requests` get the same answer on attach (actor.ts:131-135).
- **Stop.** `session.interrupt {execution_generation}` (actor.ts:170-183; Composer.tsx:131).
- **History.** A full attach sends `session.resume {display_projection:true}` and reads `display_messages`. A reconnect sends `events.since` together with `resume {omit_messages:true}`. Older rows come from `session.transcript {order:'latest', limit:200}` (actor.ts:104-129,275-298). `parseRows` keeps each turn's `row_id`s, and the user row comes first (parse.ts:464-490). It ignores `reasoning`, `display_kind` and `todo_state`.
- **Meta.** `session.info` and `session.updated` update title, revision, queue, model and generation. Auto-titles therefore show up in the chat and in the sidebar list (parse.ts:272-286; hub.ts:145). A `session.updated` for rewind, compress, reset or branch only moves the fences. The rewound or compressed turns stay on screen.
- **Model.** `model.options` plus `session.mutate model`, with the confirm token and a deferred pick (actor.ts:217-252; HW:apps/desktop/src/renderer/composer/ModelPicker.tsx).
- **Slash.** The menu shows the catalog's commands that the gateway runs and the desktop is offered, plus skills. `command.dispatch` runs them. `/title` is handled locally as a rename. An unlisted `/word` goes to the agent as text (parse.ts:663-696; hub.ts:299-317; HWP:domain/slash.ts:18-24).
- **Chat commands that exist with no UI.** `rename`, `create` and `discard` exist in the `Command` union and the IPC validators (HWP:domain/command.ts:5-30; HW:apps/desktop/src/ipc-contract.ts:117-176). The renderer sends only `open`, `start`, `send`, `stop`, `answer`, `loadEarlier`, `models` and `pickModel` (HW:apps/desktop/src/renderer/chat/Chat.tsx:116-166).
- **Chat list.** The hub's `sidebar` feed reaches IPC (HW:apps/desktop/src/main/ipc.ts:42), but no renderer subscribes. `ChatRef` can only name a bot (HWP:domain/open.ts:12), so no other session can be opened. The list calls send no `picker:true`, so `preview` and `last_active_at` are always null (HWP:sidebar.ts:40-41).
- **Extras.** Copy on the request, the reply, commands and code blocks (Thread.tsx:23,76,127), and find in the thread (HW:apps/desktop/src/renderer/chat/Find.tsx).
- **Dropped events.** `UNSHOWN` covers reasoning, `session.usage`, `todo.updated`, `subagent.*`, `status.update`, `notification.*`, `request.cancel`, `btw.complete`, `background.complete`, `moa.*`, `session.control.update` and `connection.*` (parse.ts:290-304).

## 6. Gotchas for the backend

**Fencing**
- `session.mutate` needs `request_id`, `expected_revision`, `operation` and `payload`. Any other key is `invalid_params` (GW:session_mutations.py:23,146-152).
- `expected_generation` is required for `model`, `reasoning`, `workspace`, `editor_mcp` and `edit_policy` (GW:session_mutations.py:20,150), and for `delete`, `rewind`, `reset`, `branch` and `compress` (H:persistence/authority/runtime.py:74). `rename`, `archive` and `sidebar` need none.
- `revision_conflict` and `stale_generation` refusals carry the fresh fences, and `actor.mutation` already retries once on them (actor.ts:255-268).
- A rewind requires an idle session and refuses with `session_busy` (H:persistence/sqlite/authority/_mutation.py:168-173). It bumps `runtime_generation` (:196), so read the new generation from `session.updated.execution_generation` before the next control.
- The target must be an active user row. A row that compaction archived is refused as `invalid_params` with a "compacted" detail (:174-182). Display rows carry no `archived` flag, so use the resume `messages` rows, as Desktop does, or handle that refusal.
- A rewind whose reply was lost must be re-sent with the same `request_id` and payload, never re-derived. A fresh derive would take back one more turn (HD:api/canonical-protocol.ts:332-353,362-386).
- Turns bump the revision without `session.updated`. The only place a viewer learns it is `session.info.revision` (GW:session_authority.py:486-496).
- `session.interrupt`, `session.steer` and `session.redirect` need the running `execution_generation`. Approval and clarify answers need the prompt's own generation. `prompt.resolve_unknown` needs the unknown row's generation, which `admissionOf` drops today (parse.ts:144-149).
- `session.steer` answering `rejected` with `delivered:false` is safe to resubmit as a prompt. A plain `rejected` may already have reached the agent, so never resend it (TC:canonical_sessions.py:313-321).

**Closed key sets** (4001 `invalid_params`, with `fields` from the contract check at GW:session_controls.py:356-359)
- `approval.respond` takes exactly `{session_id, execution_generation, prompt_id, choice}`, and `clarify.respond` the same with `answer` (GW:session_controls.py:995-1004). `profile` is stripped first for the `_PROFILE_IMPLICIT` verbs (:115-120,343-349).
- `image.attach_bytes`: `{session_id, profile, content_base64, data, filename, ext}`, all strings (GW:session_images.py:10-11).
- `file.attach`: `{session_id, profile, path, data_url, name, staged_upload}` (GW:session_ancillary.py:146-149).
- `prompt.btw` and `prompt.background`: `{session_id, profile, text}` (GW:session_tui_side.py:33-38).
- `complete.path`: `{session_id, profile, word, cwd}`, all strings.
- `rollback.*`: the per-verb sets at GW:session_tui_ops.py:203-205.
- `message.react`: GW:session_reactions.py:13.
- `subagent.steer`: `{session_id, profile, subagent_id, text}` (GW:session_ancillary.py:41).
- `session.control`: `{session_id, profile, action, args}`.
- `prompt.submit.attachments` items: exactly `{path, mime}`, at most 10, mime in the four image types (GW:session_ingress_media.py:159-163).
- Mutate payloads are closed per operation. `rewind`: `{target_message_id: int>0, preserve_compaction_handoff?: bool}`. `branch`: `{title?, through_message_id?: int>0, mcp_servers?}`. `sidebar`: a non-empty subset of `METADATA_FIELDS`. `reasoning`: `{effort}` (H:persistence/authority/runtime.py:299-366).

**Socket binding**
- `image.attach_bytes`, `file.attach`, `prompt.btw` and `prompt.background` refuse with `permission_denied` unless the session is attached on this socket. After a reconnect, re-resume first. `btw.complete` and `background.complete` ride this connection's subscription.

**Server requests**
- Highwing's -32601 decline settles sudo, secret and vault prompts as skipped and cancels a clarify batch, for every viewer. Once Highwing shows some of them, decline only what it cannot show, and decide whether to answer the rest at all. Leaving one unanswered lets another viewer answer it, but stalls the agent up to 120 s when Highwing is the only viewer.
- Close a card on `request.cancel {id, method, reason}`. The reasons are `timeout`, `interrupted` and `resolved` (GW:session_server_requests.py:195-208; TC:server_requests.py:373-388).
- An open request comes back on `session.resume` and `session.events.since` as `open_requests` (GW:session_controls.py:768-769).
- Only a socket attached with `session:respond` may answer (GW:session_server_requests.py:55-69).

**Untyped or unparsed events that need hand-typing**
- `approval.request`, `clarify.request` and `*.settled` (already hand-typed).
- `session.updated` per operation. Rewind adds `rewound_count`, `target_message{id, content, timestamp, …}`, `new_head_id` and `replacement_message_id` (_mutation.py:197-198). Branch adds `branched_session_id`. Compress adds `status`/`lines`. Every receipt also carries `{session_id, revision, execution_generation, operation}` (_mutation.py:99-101).
- `agent.step {iteration}` and `session.tools_changed`.
- `persisted_turn.user_row_id` and `final_assistant_row_id` are typed but unparsed.
- `status.update {kind, text}` and `notification.show {text, level, kind, key, ttl_ms, detail}` are typed.
- `btw.complete` and `background.complete` arrive with a seq but no execution generation. They are side answers, not turn events.

**Display-row shape**
- `parseRows` opens a new turn on every user row. A `/steer` row (`display_kind:'steer'`) and a skill invocation (`display_kind:'skill_invocation'`) are user rows, so steer support will split one turn into two unless `display_kind` is read.

**List**
- `preview`, `last_reply`, `last_active_at` and `pinned` come only with `session.list {picker:true}` (TC:canonical_sessions.py:197-219). HWP:sidebar.ts:40-41 does not send it.

**Contract drift**
- contract.version.json names `caafe5389ae5`, a commit that is not in the be787439 checkout. The schemas compared for this pass match the source (`CanonicalPendingAdmission`, `PersistedTurn`, `CanonicalPendingPrompt`, `ToolCompletePayload`, `TranscriptMessage`, the sudo/secret params, and the gap methods' params). Run `pnpm contract:drift` anyway.

**Scripted test gateway** (HWP:testing/gateway.ts)
- Only `HANDLERS` (:238-298) answer by themselves. Every other method goes to `story()`, which requires the fixture's next step to be `{await: <method>}`. Otherwise it fails the whole replay with "the story did not expect …" and answers -32603 (:460-473).
- A method missing from both `HANDLERS` and the vendored OpenRPC gets -32601 (:428-429), even when real Hermes serves it through the legacy fallback.
- `checkParams` runs the vendored schema. A canonical-only method refuses extra and missing keys. A shared one refuses extra keys and wrong types (HWP:testing/params.ts:110-123).
- `approval.respond` and `clarify.respond` must carry exactly four keys, come from a socket attached to the story session, and name the running generation (:121-128).
- Non-model `session.mutate` checks only that the session is known. It simulates no revision or generation fence and emits no `session.updated` (:296), so a fixture must push both.
- Bot Chat sessions accept only `session.resume`, `session.events.since`, `prompt.submit`, `model.options` and `session.detach`. Anything else is `unsupported_command` (:302-315,454-458).
- The snapshot always has `todo_state: null` and no `pending_connection`, and `display_messages` equals `messages` (:198-216).
- Server-request answers are dropped silently, and only from an attached socket (:390-400). It never emits `request.cancel`.
